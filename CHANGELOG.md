# Changelog — Skills Validation & Fixes

## Date: 2026-05-19 — SC-02 Fase 8: PR Review Workflow (pbs-pr-review-*)

Scope SC-02 — workflow nuevo de **reviewer enablement** para revisar PRs ajenos sin gastar 1-2 días leyendo código. Paralelo a Workflow A (new project) y Workflow B (existing codebase). Diferenciador clave: búsqueda de precedentes con cita textual obligatoria, separación Reviewer Dossier vs Developer Report, y triage adaptativo. Detalle completo en `.pbs-framework/scopes/SC-02-pr-review-workflow/scope-record.md`.

### New Skills Added (familia pbs-pr-review-*)

#### pbs-pr-review-context — Entry point del workflow de review
- **File:** `skills/pbs-pr-review-context/SKILL.md`
- **Purpose:** Toma `branch + base`, corre `git diff` local, mapea archivos por responsabilidad (core/soporte/test/boilerplate), detecta stack, reconstruye intención del PR (commits + `gh` opcional), aplica triage (chico/mediano/grande/sensible donde sensible domina), y produce `review-context.md` con review plan adaptativo.
- **Integration:** Entry point. Output consumido por todos los demás skills `pbs-pr-review-*`.

#### pbs-pr-review-consistency — Búsqueda de precedentes en el codebase
- **File:** `skills/pbs-pr-review-consistency/SKILL.md`
- **Purpose:** Busca precedentes (tipos, campos, utilidades, funciones, schemas) para elementos que el PR introduce. **Sin cita textual del precedente no hay finding** — sospechas bajan a review-question. Búsqueda por capas (grep → headers → función), nunca lecturas de archivos completos. Es el diferenciador del workflow vs herramientas comerciales.
- **Integration:** Llamado después de pbs-pr-review-context. Appenda a `findings.md`.

#### pbs-pr-review-general — Pase de calidad general
- **File:** `skills/pbs-pr-review-general/SKILL.md`
- **Purpose:** Revisa archivos core del PR: over/under-engineering, dead code, DRY, weak test assertions, missing edge cases comparando tests vs intención. **NO ejecuta** skills de best-practices del stack — los recomienda manualmente al reviewer (typescript-best-practices, nodejs-best-practices, etc.) según Decision 5 del scope.
- **Integration:** Llamado después de pbs-pr-review-context. Appenda a `findings.md`.

#### pbs-pr-review-security — Threat model ligero sobre deltas
- **File:** `skills/pbs-pr-review-security/SKILL.md`
- **Purpose:** Threat model centrado EXCLUSIVAMENTE en lo que el PR introduce o cambia — no audita deuda histórica del repo. Checklist: input validation, authn/authz, error leakage, data exposure, secrets/tokens, idempotencia, external calls. Para PRs chicos sin áreas sensibles permite early-exit con "sin hallazgos" sin inventar findings; para triage `sensible` siempre corre full.
- **Integration:** Llamado después de pbs-pr-review-context. Appenda a `findings.md`.

#### pbs-pr-review-reports — Genera Reviewer Dossier + Developer Report
- **File:** `skills/pbs-pr-review-reports/SKILL.md`
- **Purpose:** Skill terminal del workflow. Consume `review-context.md` + `findings.md` (si existe) y emite dos artefactos: Reviewer Dossier (para el revisor humano) y Developer Report (para el autor del PR, con doble sección: humana + LLM-actionable con prompts copy-paste por finding). Soporta modo MVP (sin findings.md → solo Dossier mínimo) y modo Full. Aplica schema de findings y respeta tope orientativo de longitud 500 líneas.
- **Integration:** Llamado después de pbs-pr-review-context (MVP) o pbs-pr-review-{consistency,general,security} (Full). Output compartido manualmente con el autor del PR — sin bots de comentarios inline.

### Decisiones Resueltas

Las 8 decisiones pendientes del Scope Record SC-02 fueron resueltas en `phase-08/spec.md`:
1. Naming: `pbs-pr-review-{context,consistency,general,security,reports}` — confirmado
2. Ubicación de artefactos: `.pbs-framework/reviews/<branch-slug>/` (equipo decide via `.gitignore`)
3. Schema de findings: P0/P1/P2/info + confianza alta/media/baja + evidencia textual obligatoria + impacto + sugerencia humana + prompt-llm opcional
4. Triage thresholds: chico ≤5 / mediano 6-20 / grande >20 / sensible = áreas sensibles (auth, pagos, datos sensibles, migraciones, permisos, jobs, queues, integraciones externas, contratos, wallets, tokens, balances) — sensible domina sobre conteo
5. Integración con best-practices: **manual**, el general-skill recomienda pero NO invoca automáticamente
6. Adaptive depth: review-plan dentro de review-context.md, los demás pases lo leen al inicio
7. Two-report structure: confirmado (Reviewer Dossier + Developer Report doble sección)
8. PR-fetching strategy: `branch + base` con `git diff` local; `gh` CLI / URL opcionales para enriquecer metadata
