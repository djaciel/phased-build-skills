# Review Fixes

## Overview

Resolve findings from a review report generated by pbs-pr-hardening. This is NOT blind implementation — it's a disciplined response to code review with technical rigor.

**Core principle:** Verify before implementing. Push back with reasoning when the reviewer is wrong. The human is the final arbiter.

**Announce at start:** "I'm using the pbs-review-fixes skill to resolve findings in the review report for phase [N]."

## When to Use

- After pbs-pr-hardening generated a review-report.md with pending findings
- When the human asks to address review findings
- Resuming resolution after pausing for human input

## Discipline Base

This skill follows the `superpowers:receiving-code-review` discipline:
- **Verify** before implementing any suggestion
- **Push back** with technical reasoning if a finding is wrong
- **No performative agreement** — don't say "great point" or "you're right"
- **One finding at a time** — test each fix individually
- **Ask before assuming** — if a finding is unclear, ask the human

## Input

### Context Detection (Dynamic)

If the user does not specify which phase or report:

1. Scan `.pbs-framework/phases/` (or `.pbs-framework/features/[name]/phases/`) for all phase directories
2. In each, look for `review-report.md`
3. Read frontmatter — find reports with `status: in_progress`
4. If multiple found → ask human which one to resolve
5. If none found → "No pending review reports found. Run pbs-pr-hardening first."

### Required Context (load in this order)
1. Review report: `.pbs-framework/phases/phase-XX/review-report.md`
2. Phase spec: `.pbs-framework/phases/phase-XX/spec.md` (for context)
3. Phase tasks: `.pbs-framework/phases/phase-XX/tasks.md` (for context)
4. AGENTS.md (for conventions)

## The Process

### Step 1: Load and Assess

1. Read the review report
2. Count pending findings by severity
3. Present summary to human:
   - "Review report has X critical, Y important, Z minor findings pending."
   - "I'll address them in order: critical first, then important, then minor."
4. Ask: "Should I proceed with all pending findings, or do you want to select specific ones?"

### Step 2: Iterate Findings

For EACH pending finding, in order of severity (critical → important → minor):

**2a. Understand the finding**
- Read the finding description and suggestion
- Read the referenced file(s) and line(s)
- Verify the issue actually exists in the current code

**2b. Evaluate**
- Is the finding technically correct for THIS codebase?
- Does the suggestion break existing functionality?
- Does the suggestion conflict with the Decision Log or spec?
- Is this a real issue or a style preference?

**2c. Respond** (one of three actions):

**Action: FIX**
- Implement the minimum change to resolve the finding
- Run validation commands to ensure no regressions
- Update the finding in review-report.md:
  ```
  - **Status:** resolved
  - **Resolucion:**
    - **Por:** resolver
    - **Accion:** fixed
    - **Comentario:** "[what was changed and where]"
  ```

**Action: REJECT** (with reasoning)
- Present technical reasoning to the human for why this finding should be rejected
- Wait for human confirmation
- Update the finding in review-report.md:
  ```
  - **Status:** rejected
  - **Resolucion:**
    - **Por:** [resolver | human]
    - **Accion:** rejected
    - **Comentario:** "[technical reason for rejection]"
  ```

**Action: DEFER** (register as tech debt)
- Finding is valid but out of scope for this phase
- Update the finding in review-report.md:
  ```
  - **Status:** deferred
  - **Resolucion:**
    - **Por:** [resolver | human]
    - **Accion:** deferred
    - **Comentario:** "[why deferred, which phase/ticket should address it]"
  ```
- Add to Tech Debt Register (`.pbs-framework/05-tech-debt-register.md`)

**2d. Human checkpoint**

After each finding resolution, present:
- What was done (fix/reject/defer) and why
- The updated finding entry
- Ask: "Proceed to next finding?"

The human can:
- Approve and continue
- Override the action (e.g., "no, fix this one instead of rejecting")
- Pause to discuss or investigate

### Step 3: Update Report Status

When ALL findings are resolved (no `pending` remaining):

1. Update frontmatter: `status: resolved`, `resolved: [fecha]`
2. Update the "Resumen de Hallazgos" summary table with final counts
3. Update "Resultado del Review" if the verdict changed

### Step 4: Verify

**REQUIRED:** Use superpowers:verification-before-completion

1. Run ALL validation commands from tasks.md
2. Verify no regressions from fixes
3. Verify all tests still pass

### Step 5: Report

Present to human:
- Summary of resolutions: X fixed, Y rejected, Z deferred
- Any deferred items added to Tech Debt Register
- All validation commands pass
- Review report status: resolved

<HARD-GATE>
Do NOT commit until the human approves the resolution summary.
The human reviews:
1. Each resolution action and reasoning
2. That validation commands pass
3. That no regressions were introduced
After approval, commit all fixes together.
</HARD-GATE>

### Step 6: Post-Approval

1. Commit all fix changes
2. If deferred items were added to Tech Debt Register, commit that too
3. Inform: "Review fixes complete. Proceed to pbs-phase-closure."

## Common Mistakes

- **Fixing without verifying the issue exists** — the code may have changed since the review. Always check first.
- **Agreeing with every finding** — push back when the reviewer is wrong. Technical correctness > social comfort.
- **Batch-fixing without testing** — fix one finding, test, then move to the next.
- **Rejecting without reasoning** — every rejection needs a technical justification the human can evaluate.
- **Deferring to avoid work** — defer is for genuinely out-of-scope items, not for avoiding difficult fixes.
- **Not updating review-report.md** — the report is the communication channel. Every action MUST be recorded there.

## Red Flags

- "The reviewer is right, let me just fix everything" → Evaluate each finding independently. Blind agreement is forbidden.
- "This is minor, I'll skip it" → If it's pending, it needs a resolution. Fix, reject, or defer — but decide.
- "I'll fix this and a few other things nearby" → Scope creep. Only fix what the finding describes.
- "The reviewer doesn't understand the code" → Maybe. But verify before dismissing. Explain your reasoning.

## Common Rationalizations

| Excuse | Reality |
|--------|---------|
| "The reviewer is always right" | Reviewers lack full context. Push back when technically justified. |
| "This fix is too small to test" | Every fix gets validated. No exceptions. |
| "I'll defer everything to move faster" | Deferring critical or important issues defeats the purpose of review. |
| "Let me also clean up this nearby code" | Only the finding. Nothing else. |
| "The human won't care about this minor" | Present it. Let the human decide. |
